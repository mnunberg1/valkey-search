# Pull Request Guidelines

This document outlines guidelines for understanding and processing pull
requests (on github) in repository ${REPO}

## Goals

- Ensure that pull requests are properly handled
- Ensure that high-effort/high-quality pull requests get the required
    attention
- Ensure that low effort/low quality pull requests are quickly commented
    on and rejected in order to eliminate line noise


## High Quality PRs

High quality PRs are ones which consist of mainly non-LLM generated code
that contains human written comments, and whose changeset is properly
segmented between commits, that is, each commit tells a story of a different
conceptual change within the PR.

The PR description is concise and free of implementation details, unless those
details are concise and important for external consumers of the PR.

The PR contains tests, but the tests are both comprehensive coverage wise
and minimal code-wise.

## Low Quality PRs

Low quality PRs consist mainly of LLM-generated code and especially
LLM-generated comments, with large numbers of changes crammed into a single
commit, making it difficult to itemize all the items changed within the
pull request.

The PR description is length and LLM-generated, featuring multiple
layout elements and tables, but ultimately failing to explain what serious
problem it solves and why it needs to be so big or implemented in this
specific kind of manner (but still spares no detail in explaining what
it does).

It contains many tests, but those tests are so long that it's impossible
for a human to read it within a reasonable amount of time and understand
its purpose.


### High vs Low Quality

A high quality PR is easily readable by a human and shows considerable
effort and time in making it comprehensible and meshing it with accepted
standards and style guidlines.

A low quality PR is disorganized and generated by a machine using a series
of LLM prompts.

### Reviewability vs Correctness

Code can be reviewable and it can be correct, sometimes it is correct but
not reviewable, and sometimes it is reviewable but not correct.

1. Strictly speaking, purely _correct_ code is code that unambiguously
improves a project, for example, fixing a typo or repairing an off-by-one
error. These kinds of changes fix a program without adding any additional
overhead in any dimension.

2. Other forms of code may be _correct_ in the sense that they do not crash
the program or return incorrect results, but may be designed in
such a way where there are unknown, unintended, or unwanted side effects
elsewhere.

3. Other forms of code may still be free of unwanted side effects, but are
structured or designed in such a way which places a future burden on
reading or understanding the codebase, or places future development constraints
(e.g. by extending an abstract interface for mandatory implementation)

4. Other forms of code may place a different kind of burden, such as an
administrative overhead on a type of dependency, or using architecture or
platform specific code, or additional interfaces which are highly specific.

None of these categories are within the scope of this document. Our aim here
is to specify very generic properties of pull requests in order to make it
simpler for our diverse and distributed contributor and development community
to further contribute, use, and understand the projects of our ecosystem.   `


## LLM Generation and Contribution Guidelines

LLM is an inevitable part of the SDLC (Software Development Life-Cycle)
and my aim is not to argue for its merits or drawbacks, but to specify how
LLMs can be used to augment and improve open-source community projects,
rather than act as a hindrane.

1) Code _structure_ should remain human readable. While LLMs may not be able to
    generate perfectly nice and human-readable implementations, the code
    structure, architecture, and framework should have some human forethought
    into it. No *vibecoding* anything into our projects

2) No multi-line LLM comments. Code should be self-documenting, and any LLM
    comments should be strictly explaining parameters or return values, and
    NOT providing rationale for X or Y design decision. Either write the
    comment yourself, or leave it out.
    Comments should explain WHAT the code does as well as WHY it does, but
    this requires a human touch to understand what is too much and too little
    explanation in context.


3) Keep commits atomic. Even if you combine multiple changes into a single
    pull request, try to isolate each change to its own commit. This is
    especially easy to do with LLMs, since they can test and verify that
    each commit is indeed self-contained and compiles independently. This
    is important for tools such as git bisect

4) Annotate LLM-driven contributions. If entire files or large functions
    are generated via LLM, they should be declared on top as being
    LLM-generated. The same goes for PR descriptions and comments.

    Knowing that something is LLM-generated helps humans determine how
    much effort should be spent into deciphering the logic and correctness.
    For example, LLMs usually don't make off-by-one errors but are awful at
    following stylistic guidelines. Humans are the opposite.



### Limit LLM Interface Surface Area

Any logical or physical segment of code should be *either* LLM _or_
human-generated, but not both. Humans and LLMs have different reasoning modes,
and employ semantics differently. Too many cooks spoil the pot, and this is
certainly the pot, and this is certainly the case with software, even software
that is purely human written and contains many maintainers.

It is therefore preferrable for LLM-generated code to occupy its own set of
functions, modules, or files and have its correctness verified by rigorous
testing and observation.

Human code, on the other hand, has a kind of internal thought pattern
associated with it, and it is often easy to understand the quality of human
code simply by reading it.

Therefore, LLM generated code should live in its own black box, as a library
or implementation of a *human* defined and derived API.

PRs should be looked at negatively when AIs *extend* existing APIs (internal
or external), or *modify* existing fields and structures without justification,
because chances are that a human would not have done the same.

When this black box **does** exist, the contributor MUST indicate where/how
this LLM black box is used, in order to instruct the reviewer where to look
and where NOT to look. Contributors should take extra care to indicate where
human control ends and machine implementation takes over.

## The Golden Rule of LLM Reviewing

The original Golden Rule "Do not do unto others what you do not want done
to yourself" can be recast in terms of LLM reviewing and generation:

- Do not have LLM write any code that you wouldn't write yourself
- Do not have LLM generate any code that you wouldn't review yourself
- Do not generate a PR in such a manner where the human time the author
    spent generating it is less than the human time the reviewer spends
    reviewing it.

## AI Reviewers (GReptile, CodeRabbit, etc)

While these tools are helpful as internal audits and nitpicks, they generate
far too much line noise far too early in the review process. These tools
should be set to their laxest setting initially to filter our constructs
and patterns that are clearly wrong, e.g. off-by-ones, typos, clear deadlocks,
null dereferences.

They should be consolidated in a single review agent that highlights
obvious issues in the code *before* any human reviewer touches it.

Things like tests and more nitpick-like comments can and should be triggered
by reviewers *after* passing initial quality sanity checks (human and
AI-derived)
